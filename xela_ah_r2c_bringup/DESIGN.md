# Design Document — `xela_ah_r2c_bringup`

## 1. Purpose of This Document

This document describes *how* `xela_ah_r2c_bringup` is built: the macro/file architecture, the sensor composition hierarchy, the left/right symmetry strategy, the taxel/sensor naming convention, and the known limitations and technical debt. See `PRD.md` for *why* the package exists and what it must satisfy; see `README.md` for day-to-day build/launch instructions.

## 2. Runtime Architecture

### 2.1 Runtime graph (`launch/xacro_launch.py`)

```
xela_sensor (launch arg) ──▶ urdf/<xela_sensor>.xacro ──▶ xacro ──▶ robot_description
                                                                         │
                                          ┌──────────────────────────────┼───────────────────────────┐
                                          ▼                              ▼                            ▼
                                 robot_state_publisher          joint_state_publisher_gui           rviz2
                                 (robot_description → /tf)      (synthetic /joint_states)     (-d <rviz_config_file>)
```

`joint_state_publisher_gui` publishes `/joint_states`; `robot_state_publisher` combines that with the static `robot_description` to publish `/tf` and `/tf_static`; `rviz2` subscribes to both to render the model and let a developer drag joint sliders and immediately see the sensor/mesh geometry respond. This is a pure visualization loop — no controller, no hardware, no MoveIt.

### 2.2 File tiers

The package deliberately separates **macro definitions** from **things you actually launch**, in three tiers:

1. **Macro-only core** — `urdf/allegro_hand_{left,right}_r2c.xacro`. Defines the `allegro_hand_{left,right}_r2c` macro (and the shared `finger` / handed `thumb_{left,right}` sub-macros) and nothing else. Not meant to be rendered by itself; always `xacro:include`d by something that also defines a `parent` link and calls the macro.
2. **Hard-coded demo wrappers** — `urdf/allegro_hand_{left,right}_curved.xacro`. Include the macro file, define a `world` link, and call the macro with literal arguments (`sequence="0" tips="curved" parent="world" defaultnames="1" palm="1" taxels="1" sensor_collision="0"`). Nothing is overridable from the command line; these exist purely as a quick, guaranteed-to-work "does the macro still render" smoke test.
3. **Parameterized wrappers** — `urdf/x_allegro_{left,right}_curved.xacro` and `urdf/x_allegro_{left,right}_w_ur_adapter.xacro`. Declare `xacro:arg`s (`taxels`, `sensor_collision`, `tips`, `sequence`, `defaultnames`, `palm`, `parent`), conditionally create the `world` link only when `parent == 'world'` (so the same file can also be attached under an existing robot, e.g. a UR arm's adapter link), and forward the args into the macro call. These are the files real command-line/launch overrides should target.

A fourth category, `urdf/x_allegro_{left,right}_no_taxel.urdf`, is a **generated snapshot** (auto-generated header: "This document was autogenerated by xacro from ... EDITING THIS FILE BY HAND IS NOT RECOMMENDED"). It is a build artifact checked into source control, not a hand-maintained source file.

This three-tier-plus-snapshot pattern is the one `xela_dg5f_bringup` deliberately replicates: a macro-only `x_dg5f_hand.xacro`, a demo `x_dg5f_right_standalone.xacro` wrapper, and (eventually) an `x_dg5f_left_standalone.xacro` counterpart.

## 3. Macro Signature and Parameter Semantics

```
allegro_hand_right_r2c / allegro_hand_left_r2c (params):
  sequence parent
  x:=0.0 y:=0.0 z:=0.0 rx:=0.0 ry:=0.0 rz:=0.0
  covers:=1 phalanges:=1 tips:='flat' palm:=1 taxels:=1
  defaultnames:=0 sensor_collision=0
```

| Param | Meaning | Notes |
|---|---|---|
| `sequence` | Namespace prefix applied to every generated link/joint name. | Empty string ⇒ single-hand mode, no prefix. Lets multiple hand instances coexist in one URDF. |
| `parent` | Link this hand's `hand_root` attaches to, via a fixed joint. | The hand is never forced to be a standalone robot rooted at a fixed base — this is the property that lets any arm Xacro `xacro:include` and instantiate it in place. |
| `x y z rx ry rz` | Palm mount offset/orientation relative to `parent` (angles in degrees, converted internally with `radians()`). | |
| `covers` | Adds separate `_cover` links/fixed joints (rubber/plastic protective shells) on finger links, using dedicated cover meshes (`link_1_cover.stl`, `link_2_cover.stl`, `thumb_1_cover.stl`, `thumb_2_cover.stl`). | Also changes mass/inertia (a covered link is heavier). Convention in the source comments: *"covers are always with sensors"* — covers are treated as a property of the sensorized build, not an independent cosmetic choice. |
| `phalanges` | Selects sensorized ("`_ext`"/normal) vs. non-sensorized ("`_ns`") mesh sets for finger link 1/2 and the thumb, and swaps mass/inertia accordingly. | |
| `tips` | `'flat'` → `uSFtAH` (flat fingertip sensor, composed from `uSPa44`), `'curved'` → `uSCuAH` (30 hand-placed taxels following the curved tip surface), `'default'` → `aftdn` (no-sensor placeholder tip, mesh `ahft_default.STL`). | Only one tip macro is instantiated per finger, selected by string comparison. |
| `palm` | Sensorized palm mesh (`base_new_{right,left}.stl`) + three `uSPa46_2409` (4×6, 24-taxel) patches vs. non-sensorized palm mesh (`base_{right,left}_ns.stl`) with none. | |
| `taxels` | Forwarded into every per-sensor macro call; gates whether individual taxel point links/joints are instantiated inside an otherwise-always-present sensor housing/patch body. | Housings represent real hardware and are unconditional; `taxels` only controls the fine-grained deformable sensing points — this is the exact convention `xela_dg5f_bringup`'s `x_dg5f_hand.xacro` copies verbatim, including the "planning model uses `taxels=0`, a separate `/robot_description_full` uses `taxels=1` for visualization" split used by downstream MoveIt Pro packages. |
| `defaultnames` | `1` → numeric `finger_num` (0–3) generic naming; anything else → legacy Japanese-named sequence prefixes: `oya_finger_` (thumb), `hitosashi_finger_` (index), `naka_finger_` (middle), `kusuri_finger_` (ring). | Both branches instantiate identical geometry; only the `x_seq` sensor-name prefix differs. This is a naming-scheme compatibility toggle, not a geometry toggle. |
| `sensor_collision` | Forwarded down to disable/enable `<collision>` geometry on individual taxel spheres. | Off by default in most demo wrappers for performance — a hand can have dozens of taxel spheres, and collision-checking all of them is expensive. |

### 3.1 Sub-macros

- **`finger`** (shared, *not* handedness-suffixed) — params: `x_seq b_seq parent finger_num offset_origin_x offset_origin_y offset_origin_z finger_angle_r covers:=1 tip:='flat' phalanges:=1 taxels:=0 sensor_collision:=1`. Builds the 4 revolute joints (`ah_joint{N}0..3`) and 4 links (`ah_link_{N}0..3`) of one Allegro finger. Joint limits are narrowed by ±0.1 rad from the vendor Allegro spec (e.g. `lower="${-0.57+0.1}" upper="${0.57-0.1}"`) — a deliberate safety margin baked into the macro rather than left to a downstream joint-limits YAML. `uSPa44` (4×4, 16-taxel) patches are placed on link_1 (two patches) and link_2 (one patch) when `phalanges==1`.
- **`thumb_right` / `thumb_left`** (handedness-suffixed, unlike `finger`) — params: `x_seq b_seq parent finger_num offset_origin_x offset_origin_y offset_origin_z finger_angle_r finger_angle_p finger_angle_y covers:=1 phalanges:=1 tip:='flat' taxels:=0 sensor_collision:=1`. The thumb has a distinct kinematic chain and mesh set (`link_12.0_{right,left}.STL`, `link_13.0.STL`, `thumb_1.0.stl`, `thumb_2.0.stl`) and mirrored joint axes between hands, so it cannot share a single macro the way the three fingers do. Two `uSPa44` patches (link_2, link_3) plus a tip sensor on link_3.
- Inertial values throughout are **hard-coded per configuration** (a 4-way branch on `tip` for the regular fingertip link, a 6-way branch of `covers`×`phalanges`×`tips` combinations on the thumb tip link) rather than computed from mesh volume — the source comments mark this intentionally (`<!--6 options-->`, `<!--covers are always with phalange sensors-->`). This is real measured mass/inertia data, not a placeholder.
- The `thumb_*` joints additionally carry `<dynamics damping="..." friction="...">` tags; the `finger` macro's joints do not. This asymmetry is inherited, unreviewed technical debt — see Section 6.

## 4. Sensor Composition Hierarchy

The sensor macros compose bottom-up, from `xela_models`:

```
taxel_n.xacro            (atomic: one prismatic "give" joint + one 1mm sphere link)
   └─ uSPa44.xacro        (4x4 = 16 taxels, grid-stepped placement; used on finger phalanges + thumb)
   └─ uSPa46_2409.xacro   (4x6 = 24 taxels, grid-stepped placement; used on palm, 3 instances/hand)
   └─ uSCuAH.xacro         (30 taxels, individually hand-placed x/y/z/rx/ry/rz; curved fingertip)
        uSFtAH.xacro       (flat fingertip: intermediate positioning frame + reuses uSPa44 with body:=0)
        aftdn.xacro         (no-sensor tip placeholder mesh, zero taxels)
```

- **`taxel_n`** is the atomic unit: a `prismatic` joint (range `${-0.001-zmod}` to `0.000`) representing a small deformation "give," plus a 1 mm sphere link. Collision and inertial geometry on the sphere are opt-in flags (`sensor_collision`, `sensor_inertial`), defaulted off, because a full hand can instantiate dozens to over a hundred of these.
- **`uSPa44`**/**`uSPa46_2409`** are flat rectangular patches that place their taxels via simple grid arithmetic (`${n*txstep+xoff}`, row-by-row), which only works because the patch's mounting surface is flat.
- **`uSCuAH`** (curved fingertip) cannot use that grid formula because it must conform to a curved 3D surface, so each of its 30 taxels has an individually specified x/y/z/rx/ry/rz — a direct consequence of the physical sensor's shape, not an arbitrary implementation choice.
- **`uSFtAH`** (flat fingertip) is a good example of composition-over-duplication: rather than re-placing 16 taxels itself, it builds two small intermediate frames (a tilted positioning joint at `xyz="0.0 0.0140 0.0010" rpy="${radians(-25)} 0 0"`, then a pure-rotation joint `rpy="0 0 ${radians(-90)}"`) and then instantiates `uSPa44` (with `body:=0`, since the fingertip shell is the visual body, not the patch mesh) on top of that frame. The flat fingertip is, physically and in the model, a `uSPa44` patch mounted at a specific angle inside the fingertip shell.

## 5. Left/Right Symmetry Strategy

Symmetry between the left and right hand is **not** implemented as one mirrored macro driven by a `side`/sign parameter. It is implemented as **full file duplication with independently hard-coded mirrored constants**:

- Separate macro names per hand for the parts that actually differ in kinematics/mesh (`allegro_hand_right_r2c` vs. `allegro_hand_left_r2c`, `thumb_right` vs. `thumb_left`).
- A single **shared, non-suffixed `finger` macro**, because the three non-thumb fingers are geometrically identical between hands except for the offset signs the *caller* passes in.
- Every mirrored constant — palm mesh filenames (`base_new_right.stl`/`base_new_left.stl`), thumb mesh filenames, thumb visual-origin rotation (`rpy="0 0 0"` right vs. `rpy="${radians(180)} 0 0"` left), thumb joint axis signs (`-1 0 0` vs. `1 0 0`, `0 0 1` vs. `0 0 -1`), and palm-sensor y-offsets (`-0.021`/`0.021` right vs. `0.0249`/`-0.0249` left) — is written independently in each hand's file. There is no shared "mirror" utility macro that derives one hand's constants from the other's by formula.

**Design implication for future hands (e.g. DG-5F left variant):** this reference package's own convention favors duplicated-file-with-mirrored-literals over a single parameterized macro with a sign-flip `side` argument. `xela_dg5f_bringup` chose differently on purpose — a single `x_dg5f_hand.xacro` macro with a `side` parameter forwarded to the vendor `dg5f_hand` macro — specifically to avoid this duplication, accepting the added risk that XELA sensor placement offsets are, as of this writing, tuned and verified for the right hand only and still need equivalent visual verification for the left.

## 6. Taxel / Sensor Naming Convention

There is no single in-file comment enumerating the full naming scheme; it is implicit in how `sequence` strings are built and concatenated. Reconstructed from the macro call sites and the shipped SRDF fragment's link names:

- Every sensor patch macro takes a `sequence` string that namespaces its taxel names: `${sequence}_<SENSOR_TYPE>_<NN>`, e.g. `x_taxel_0_11_uSPa44_01`.
- **Palm** sensors use fixed sequence ids **`51`, `52`, `53`** (three `uSPa46_2409` 4×6 patches), independent of `finger_num`.
- **Finger/thumb** per-segment sequence ids follow `${finger_num}${segment}`, where `finger_num` is `0` (thumb), `1` (index), `2` (middle), `3` (ring), and `segment` is the joint/link stage digit (`0`–`3`). This produces ids like `10`, `11`, `12`, `13`, matching SRDF entries such as `base_0_ah_link_10`, `base_0_ah_link_23`, `base_0_ah_link_32`, `base_0_ah_link_33`.
- Within a single patch, individual taxels are numbered `_01`…`_16` (uSPa44, 4×4) or `_01`…`_24` (uSPa46_2409, 4×6) in row-major grid order; `uSCuAH` (curved tip) uses `_01`…`_30` with no grid formula, since positions are hand-placed.

If a downstream consumer needs an authoritative, explicitly documented sensor_pos/module-numbering table (as opposed to one reconstructed from code, as above), it should be written and committed here rather than re-derived each time — this is a documentation gap, not an implementation gap.

## 7. Known Limitations and Technical Debt

1. **RViz branch dead code** — `launch/xacro_launch.py` computes `all_sensor_view.rviz` only when `xela_sensor == 'all_parts_of_individual_module'`, a value that is not among the launch argument's declared choices. This branch can never execute; the default `urdf_rviz2.rviz` is always used unless a caller passes `rviz_config_file` explicitly.
2. **Dependency declaration gap** — `package.xml` declares `joint_state_publisher`, but the launch file actually runs `joint_state_publisher_gui`; `rviz2` and `xela_models` are used by launch/Xacro but declared nowhere in `package.xml`.
3. **SRDF fragment, not a document** — `config/allegro_hand_left_r2c.srdf` is a bare sequence of `<disable_collisions>` elements with no enclosing `<robot>`/groups/end-effectors. It must be treated as an include fragment by whatever assembles a full planning SRDF (see `ur7e_dg5f_common`'s analogous `*_base.srdf.xacro` pattern for one way to do this via `xacro:include` + `xacro:if` inside an SRDF file, which MoveIt Pro's own SRDF loader supports).
4. **No right-hand SRDF fragment** — only the left hand's disable-collisions fragment is shipped; a right-hand equivalent does not exist in this package today.
5. **Inconsistent joint dynamics tags** — `thumb_*` joints declare `<dynamics damping="..." friction="...">`; the shared `finger` macro's joints do not. Unclear whether this is intentional (thumb-specific tuning) or an oversight; not resolved by this document.
6. **Generated snapshots checked into `urdf/`** — `x_allegro_{left,right}_no_taxel.urdf` are `xacro`-generated build artifacts committed to source control. They are clearly marked "EDITING THIS FILE BY HAND IS NOT RECOMMENDED" but their intended lifecycle (regenerated when? consumed by what?) is not documented elsewhere in the package.

## 8. Relationship to `xela_dg5f_bringup`

`xela_dg5f_bringup`'s `x_dg5f_hand.xacro` was deliberately designed against this package as a reference, and intentionally diverges from it in two ways worth recording for anyone comparing the two:

- It uses a single macro with a `side` parameter instead of duplicated per-hand macro files, trading this package's "every mirrored constant is independently verified" safety for reduced duplication (at the cost of left-hand sensor offsets not yet being independently visually verified).
- It keeps the same `taxels`-only-gates-individual-points-while-housings-stay-unconditional convention, and the same `sensor_collision` flag semantics, verbatim.
